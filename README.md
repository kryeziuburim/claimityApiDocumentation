# Claimity Help Center & API Documentation

Static Next.js site (help center, manual, support form and API documentation) deployed to GitHub Pages.

## Development

Requires Node 22 (see `.nvmrc`; `fnm use` / `nvm use` pick it up). Use a 64-bit Node: Vitest's bundler has no
32-bit Windows build.

```bash
npm ci                 # also installs the pre-commit hook
cp .env.example .env   # EmailJS keys for the support form (optional locally)
npm run dev            # http://localhost:3000
```

| Script              | Purpose                                                                |
| ------------------- | ---------------------------------------------------------------------- |
| `npm run dev`       | Dev server                                                             |
| `npm run build`     | Static export to `out/`                                                |
| `npm run lint`      | ESLint (Next core-web-vitals + TS)                                     |
| `npm run typecheck` | `tsc --noEmit`                                                         |
| `npm run format`    | Prettier (`format:check` in CI)                                        |
| `npm test`          | Vitest: claim schemas, OpenAPI spec, rule texts, pure helpers          |
| `npm run test:e2e`  | Playwright + axe against the static export (run `npm run build` first) |

To use an installed browser instead of Playwright's own: `PLAYWRIGHT_CHANNEL=msedge npm run test:e2e`
(or `npx playwright install chromium` once).

### Quality gates

- **Pre-commit** (husky + lint-staged): Prettier and `eslint --fix` on staged files.
- **CI** (`.github/workflows/ci.yml`, every pull request): format, lint, typecheck, unit tests, build,
  end-to-end and accessibility tests. On failure the Playwright report (with traces) is attached to the run.
- **Deploy** (`.github/workflows/deploy.yml`, pushes to `main`): unit tests, then build and publish to GitHub Pages.
- **Dependabot**: weekly grouped npm updates, monthly GitHub Actions updates.

What the tests guard:

- every claim schema compiles, all embedded `examples` are valid, and the example generated by
  "Beispiel übernehmen" is accepted by its schema; `openapi.json` is a valid OpenAPI document
- snapshots of the rule and format texts derived from the schemas (all categories × languages)
- the API page in a real browser (desktop and phone viewport): sidebar navigation, scroll spy, payload tabs, deep links, the payload
  tester (against a mocked validation API), all localized pages and the localized 404 page; any uncaught
  page error (e.g. a hydration mismatch) fails the test
- on a phone: no horizontal overflow on any page, the off-canvas menu (open, scroll lock, navigate, close)
- WCAG 2.1 AA via axe on the main pages (serious and critical violations fail)

## Structure

```
app/
  [locale]/                  one route tree for all languages (de, en, fr, it)
    page.tsx                 help center home
    api/_components/         API documentation
      ApiPageClient.tsx      page shell: composes sidebar, sections and payloads
      api-page/              sidebar, scroll spy, navigation data, layout hooks
      claim-payload/         claim payload docs and tester (schema rules, validation)
      *Section.tsx           one component (+ .messages.ts) per chapter
    manual/ support/ legal-notice/
  page.tsx                   redirects / to the default locale
  not-found.tsx              404 page (prerendered once, switches to the URL's language)
components/
  api/                       OpenAPI rendering: EndpointCard, EndpointDetails (+ endpoint-details/), SchemaExplorer
  ui/                        shadcn/ui primitives (generated, not formatted)
lib/                         framework-free helpers (i18n, metadata, JSON Schema, clipboard, scroll, spam guard)
e2e/                         Playwright specs
scripts/serve-static.mjs     serves out/ like GitHub Pages (used by the e2e tests)
public/assets/
  openapi.json               API spec rendered on the API page
  schemas/                   JSON schemas for claim payloads
  <locale>/                  PDF guides per language
```

## Translations

Every locale-dependent component has a colocated messages file, e.g.
`OverviewSection.tsx` + `OverviewSection.messages.ts`:

```ts
const de = { title: "Übersicht" /* ... */ }
export const overviewMessages: Record<Locale, typeof de> = { de, en: {/* ... */}, fr: {/* ... */} }
```

`Record<Locale, typeof de>` makes TypeScript fail the build if a language is missing a key.
Pages get the locale from `params`; shared client components use `useLocale()` (`hooks/use-locale.ts`).

**Adding a language** (e.g. `it`): add it to `locales` in `lib/i18n.ts`, then let `npm run typecheck`
list every messages file that needs the new translations.

**Adding a page**: create `app/[locale]/<name>/page.tsx` with `generateMetadata` using `pageMetadata({ locale, path: "<name>/", ... })`.

## Known limitations

- `<html lang>` is set on the client: a correct static value needs the root layout inside `[locale]`, which in turn
  needs Next.js' `global-not-found` (still experimental).
- Next.js' static export requests some segment-prefetch files (`__PAGE__.txt` of the `[locale]` segment) under a
  different path than it writes them; prefetching those fails with 404, navigation is unaffected.
- The support form sends directly to EmailJS. Client-side spam checks (honeypot, minimum fill time, cooldown) catch
  simple bots; for more, enable EmailJS' own rate limiting / reCAPTCHA in its dashboard.
